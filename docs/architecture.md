# Architecture

The project is split into a packaged theme, a reversible Windows launcher, and a standalone showcase.

## 1. Theme packages

`themes/diana-dark` and `themes/diana-light` each contain a CodeDrobe manifest and host-scoped CSS. The manifest supplies the native appearance values and local image map; CSS handles the reversible decorative layer and small control-state refinements.

The two variants share layout rules but keep separate color, character, line-art and luminance decisions. Neither variant is generated by inverting the other.

## 2. Loopback runtime

`tools/diana-runtime.mjs` connects to Codex through a Chrome DevTools Protocol endpoint bound to `127.0.0.1:9336`. It probes the live renderer, applies the packaged theme, verifies required nodes, and can keep one watcher alive across renderer reloads.

The Windows launcher:

- records runtime state below `.runtime/`;
- replaces only older Diana watchers;
- does not keep Codex App Manager or an extra WebView2 subtree alive;
- never relaunches Codex after an intentional user close;
- can maintain the themed launch path when Codex is reopened normally;
- exposes status and full restore commands.

## 3. Simulated showcase

`preview/index.html` is an independent 1920×1080 interface simulation. It references the same final theme assets and mirrors the released theme parameters, but it does not connect to Codex or read local tasks. README screenshots and future promotional video frames are generated from this page.

## Safety boundaries

- Never modify `app.asar`, MSIX contents, signatures, or files under `WindowsApps`.
- Never inject JavaScript into Codex, analytics, remote CSS, or remote images.
- Keep every selector below the explicit `html.codedrobe-host-codex` host scope.
- Bind the debugging endpoint to loopback only.
- Record the real Codex version in compatibility notes before claiming support.
- Keep disable and restore commands available before enabling runtime changes.
- Do not use screenshot overlays that merely imitate a working theme.
